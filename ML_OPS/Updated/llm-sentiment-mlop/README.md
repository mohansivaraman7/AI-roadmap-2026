# LLM Sentiment Classifier — MLOps Reference Project

A small, complete example of fine-tuning an open-source transformer LLM
(DistilBERT) and operating it with proper MLOps practices: experiment
tracking, a model registry with alias-based promotion, automated
retraining in CI, containerized serving, and tests. It's intentionally
small (40 sample reviews, a few minutes of CPU training) so the whole
loop is runnable end-to-end, but the structure is the same one you'd use
for a much bigger dataset or model.

## Folder structure

```
llm-sentiment-mlops/
├── configs/
│   └── config.yaml          # all hyperparameters & paths — nothing hardcoded in code
├── data/
│   ├── raw/sample_reviews.csv
│   └── processed/           # generated by data_prep.py (train/val/test splits)
├── src/
│   ├── data_prep.py         # stage 1: split raw data
│   ├── train.py             # stage 2: fine-tune + log to MLflow + register model
│   ├── evaluate.py          # stage 3: score on test set, promote if better
│   └── serve.py             # stage 4: FastAPI app serving the "champion" model
├── tests/
│   ├── test_data_prep.py
│   └── test_serve.py
├── .github/workflows/ci-cd.yml   # test -> retrain -> evaluate -> build image
├── Dockerfile
├── requirements.txt
└── models/                  # local Trainer checkpoints (MLflow is the source of truth)
```

## Open-source tools used

| Purpose | Tool |
|---|---|
| Base LLM | `distilbert-base-uncased` (Hugging Face `transformers`) |
| Data handling | `datasets`, `pandas`, `scikit-learn` |
| Experiment tracking + model registry | `mlflow` |
| Serving | `FastAPI` + `uvicorn` |
| Containerization | `Docker` |
| CI/CD | `GitHub Actions` |
| Testing | `pytest` |

Everything here runs locally with no paid services required. MLflow's
tracking store defaults to a local SQLite database (`mlflow.db`), with
model artifacts under `mlartifacts/` — not the older plain-folder
`mlruns/` store, which MLflow 3.x puts into maintenance mode and refuses
to use unless you explicitly opt in. Point `mlflow.tracking_uri` in
`configs/config.yaml` at a real MLflow server URL (or a Postgres/MySQL
URI) to share it across a team instead.

## How the pieces fit together

1. **`data_prep.py`** reads `data/raw/sample_reviews.csv` and writes a
   stratified train/val/test split to `data/processed/`. Keeping this as
   its own stage means you can swap in a real data source (a database, a
   feature store, DVC-tracked files) without touching training code.

2. **`train.py`** fine-tunes DistilBERT for binary sentiment
   classification. Every run logs its hyperparameters and validation
   metrics to MLflow and registers the resulting model under the name
   `sentiment-classifier` in the MLflow Model Registry — so every trained
   model is versioned and comparable, not just a `.pt` file sitting on
   someone's laptop.

3. **`evaluate.py`** is the safety gate: it scores the newest registered
   version against the held-out test set, compares it to whichever
   version currently holds the `champion` alias, and only reassigns that
   alias if the new version is actually as good or better. This is what
   stops a regression from silently reaching production.

4. **`serve.py`** is a FastAPI app that resolves the model by
   `models:/sentiment-classifier@champion` — i.e. "whatever is currently
   promoted" — rather than a hardcoded path or version number. Promoting
   a new model via `evaluate.py` and restarting the service is the entire
   deployment step.

5. **`.github/workflows/ci-cd.yml`** ties it together: every push runs
   the fast unit tests; a push to `main` additionally re-runs the full
   data → train → evaluate pipeline and builds a Docker image from the
   result.

## Running it locally

All scripts resolve `configs/config.yaml` (and every relative path inside
it) against the project root automatically, so `python src/train.py`
works the same whether you run it from the project root, from inside
`src/`, or via an editor's "Run Python File" button (which sets the
working directory to wherever the file lives — VS Code does this, and
is the most common reason a fresh checkout fails with
`FileNotFoundError: 'configs/config.yaml'` before this fix).

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 1. Split the data
python src/data_prep.py

# 2. Fine-tune DistilBERT and register the model (a few minutes on CPU)
python src/train.py

# 3. Evaluate on the test set and promote if it's the best so far
python src/evaluate.py

# 4. Inspect runs/models in the MLflow UI
mlflow ui   # open http://localhost:5000

# 5. Serve the promoted model
uvicorn src.serve:app --reload

# 6. Try it
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"text": "This is fantastic, I love it!"}'
```

## Running the tests

```bash
pytest tests/ -v
```

`test_data_prep.py` exercises the real splitting logic against the
sample CSV. `test_serve.py` monkeypatches the model so the API layer can
be tested in CI in a couple of seconds, with no GPU and no trained model
required.

## Building & running the Docker image

```bash
docker build -t sentiment-classifier .
docker run -p 8000:8000 sentiment-classifier
```

Note the image copies `mlflow.db` and `mlartifacts/` into the container,
so train + evaluate must be run at least once before building — exactly
what the CI pipeline does automatically before the `build-image` job.

## Extending this toward a "real" setup

- **Bigger model / real LLM generation task**: swap `distilbert-base-uncased`
  for something like `google/flan-t5-small` or a Llama/Mistral variant via
  `transformers`, and switch the task head accordingly.
- **Data versioning**: add [DVC](https://dvc.org) to version
  `data/raw/` and `data/processed/` alongside Git, especially once data
  stops fitting comfortably in a repo.
- **Drift monitoring**: add [Evidently](https://www.evidentlyai.com/) to
  compare production input distributions against the training set on a
  schedule.
- **Remote tracking server**: point `mlflow.tracking_uri` at a hosted
  MLflow server (or a managed Postgres/MySQL URI) so the whole team
  shares one registry instead of a local SQLite file.
- **Real deployment target**: replace the CI's local `docker build` with
  a push to a registry (ECR/GCR/Docker Hub) and a deploy step
  (Kubernetes, Cloud Run, ECS) triggered after the image builds.
